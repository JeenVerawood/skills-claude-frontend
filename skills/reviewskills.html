_verify — ผู้ตรวจสอบความครบถ้วนสมบูรณ์ (Completeness Auditor)

verify-completeness
หน้าที่หลัก
ทำหน้าที่เป็น "ผู้ตรวจสอบจากภายนอก" — อ่านข้อข้อมูลจำเพาะ (Spec) แล้วตรวจเช็คว่าไฟล์ทั้งหมดที่ควรจะมีนั้นถูกสร้างขึ้นจริงหรือไม่ หากพบช่องโหว่หรือส่วนที่ขาดหายไป → จะทำการสร้างไฟล์นั้นขึ้นมาทันที ไม่ใช่เพียงแค่รายงานผลอย่างเดียว และจะถูกรันเป็นขั้นตอนสุดท้ายเสมอ (ขั้นตอนที่ 9)
คำกระตุ้น (Trigger Words)
verify ตรวจสอบ ครบหรือยัง check completeness มีอะไรขาดไหม
ลำดับขั้นตอนการทำงาน (ห้ามข้ามขั้นตอน)
  • ขั้นตอนที่ 1อ่านข้อข้อมูลจำเพาะจากไฟล์ CLAUDE.md — ค้นหารายการหน้าเพจ (Pages), ส่วนประกอบ (Components), ปลายทาง API (API Endpoints), สถานะ (State), และระบบสิทธิ์ (Auth)
  • ขั้นตอนที่ 2สร้างรายการไฟล์ที่คาดว่าต้องมี (Expected File List) แยกตามหมวดหมู่อย่างครบถ้วน
  • ขั้นตอนที่ 3แกะรอยตรวจสอบทุกไฟล์ — ตรวจสอบทั้งการมีอยู่ของไฟล์และเนื้อหาภายใน (✅ สมบูรณ์ / ⚠️ เป็นไฟล์โครงร่างเปล่า / ❌ ขาดหายไป)
  • ขั้นตอนที่ 3bสแกนการนำเข้าไฟล์ (Import Scan) — สแกนการคำสั่ง import ในไฟล์ page.tsx ทุกไฟล์ เพื่อค้นหาไฟล์ที่อาจจะตกหล่นไปจากรายการที่คาดไว้
  • ขั้นตอนที่ 4แสดงรายงานความครบถ้วนสมบูรณ์ (Completeness Report) พร้อมตารางสรุปผล
  • ขั้นตอนที่ 5แก้ไขอัตโนมัติ (Auto-Fix) — ดำเนินการสร้างไฟล์ที่ขาดหายไปในทันที โดยไม่ต้องรอให้ผู้ใช้งานสั่งการ
  • ขั้นตอนที่ 6คำตัดสินสุดท้าย (Final Verdict) — แสดงสถานะ ผ่าน ✅ หรือ ไม่ผ่าน ❌

00-req-spec

folder-types — ผู้ออกแบบโครงสร้างสถาปัตยกรรม (Structure & Architecture)

02-folder-types
หน้าที่หลัก
กำหนดมาตรฐานโครงสร้างโฟลเดอร์, ระบบนามแฝงของเส้นทาง (Path Alias), และระเบียบข้อบังคับในการจัดหมวดหมู่ส่วนประกอบ (Component) สำหรับระบบ Next.js App Router ทำหน้าที่เป็น "สถาปนิกซอฟต์แวร์" ที่จะท้าทายและตรวจสอบความเหมาะสมของโครงสร้างก่อนอนุมัติใช้งานจริง
คำกระตุ้น (Trigger Words)
วางไฟล์ที่ไหนดี โครงสร้าง project แยก component ยังไง import path ยาวมาก folder structure
โครงสร้างโฟลเดอร์มาตรฐาน (ระดับราก - Root Level, โดยไม่มีโฟลเดอร์ src/)
โฟลเดอร์สิ่งที่ต้องจัดเก็บภายใน
app/จัดเก็บเฉพาะไฟล์ระบบเส้นทางเท่านั้น (เช่น page.tsx, layout.tsx, route.ts)
components/จัดเก็บส่วนประกอบทั้งหมด — แยกประเภทฝั่งผู้ใช้งานด้วยการลงท้ายชื่อไฟล์ด้วย *Client.tsx
lib/จัดเก็บไฟล์ฟังก์ชันส่วนกลาง เช่น auth.ts, db.ts, env.ts, utils.ts, mockData.ts
models/จัดเก็บโครงสร้าง Mongoose models (เฉพาะในโครงการที่เป็น Full-stack เท่านั้น)
types/ไฟล์ index.ts — สำหรับรวบรวมอินเทอร์เฟซ (Interface) และไทป์ทั้งหมดไว้ในไฟล์เดียว
รูปแบบการจัดการส่วนประกอบ (Component Pattern)
  • *Client.tsxจำเป็นต้องระบุคำสั่ง 'use client' ไว้ที่บรรทัดแรกสุดของไฟล์ — สำหรับส่วนประกอบที่มีการใช้ useState/useEffect หรือเข้าถึง Browser API
  • *.tsxปลอดภัยสำหรับการทำงานฝั่งเซิร์ฟเวอร์ (Server-safe) — ทำหน้าที่รับค่า Props เพื่อนำไปแสดงผลเพียงอย่างเดียว โดยไม่ต้องใส่ 'use client'
ระบบนามแฝงของเส้นทาง (Path Alias ในไฟล์ tsconfig)
"@/*": ["./*"] — แผนผังอ้างอิงตรงไปยังโฟลเดอร์ราก (Root) โดยไม่มีการผ่านโฟลเดอร์ src/
ตัวอย่างรูปแบบการใช้งาน: import { cn } from '@/lib/utils'
รูปแบบที่ไม่พึงประสงค์และพบบ่อย (Anti-patterns)
  • มีไฟล์ส่วนประกอบ (Component) ปะปนกระจายอยู่ภายในโฟลเดอร์ app/
  • การนำเข้าไฟล์รูปแบบอ้างอิงสัมพันธ์ (Relative Import) ที่มีความลึกเกินกว่า 2 ชั้น (เช่น ../../../../...)
  • การเขียนนิยามประเภทข้อมูล (Type Definitions) กระจัดกระจายอยู่ทั่วไป แทนที่จะรวมไว้ที่โฟลเดอร์ types/index.ts
  • การใช้คำสั่ง 'use client' ครอบคลุมไฟล์โครงร่างหลัก (Layout) หรือหน้าเพจ (Page) ทั้งหมดโดยไม่จำเป็น

nextjs-render — ระบบจัดการการแสดงผล Next.js (Next.js App Router)

  • ชั้นที่ 1Request Memoization — ป้องกันการดึงข้อมูลซ้ำซ้อน (Dedup Fetch) ภายในรอบการแสดงผลเดียวกัน

react-hooks — รูปแบบและโครงสร้าง React (React Patterns)

04-react-hooks
หน้าที่หลัก
ควบคุมและจัดการการใช้งาน React hooks และรูปแบบส่วนประกอบอย่างถูกต้อง: การจัดการตัวแปรอ้างอิงของ useEffect (Dependencies), ปัญหาฟังก์ชันจำค่าตัวแปรเก่า (Stale Closure), ปัญหาการเรนเดอร์ซ้ำซ้อนโดยไม่จำเป็น (Unnecessary Re-render), การใช้ useCallback/useMemo และการจัดการ Context ทำหน้าที่เป็น "ผู้จับคู่รูปแบบปัญหา" — จำเป็นต้องระบุรูปแบบโครงสร้างที่มีปัญหาก่อนเสนอแนวทางแก้ไข
คำกระตุ้น (Trigger Words)

รูปแบบปัญหาทั่วไปที่ต้องระบุให้ชัดเจนก่อนทำการแก้ไข
  • Stale Closureฟังก์ชันเรียกใช้งานค่าสถานะ (State) หรือคุณสมบัติ (Prop) ตัวเก่าภายในคำสั่ง Callback หรือ useEffect
  • Infinite Loopมีการใส่วัตถุ (Object) หรืออาร์เรย์ (Array) ไว้ในกล่องตัวแปรอ้างอิงของ useEffect ทำให้อ้างอิงตำแหน่งหน่วยความจำใหม่ทุกครั้งที่เกิดการเรนเดอร์
  • การเรนเดอร์ซ้ำซ้อนการที่ส่วนประกอบหลัก (Parent Component) เกิดการเรนเดอร์ใหม่ ส่งผลให้ส่วนประกอบย่อย (Child Component) ต้องเรนเดอร์ซ้ำตามไปด้วยโดยไม่มีความจำเป็น
  • ขาดการคืนหน่วยความจำการใช้งาน useEffect ที่มีการติดตามข้อมูล (Subscription) หรือตัวนับเวลา (Timer) แต่ไม่ได้เขียนฟังก์ชันล้างค่าข้อมูล (Cleanup Function) รองรับไว้

ts-zod — ระบบชนิดข้อมูลและการตรวจสอบโครงสร้าง (TypeScript & Zod)

หน้าที่หลัก
จัดการโครงสร้างคำนิยามประเภทข้อมูลของ TypeScript, ระบบตรวจสอบความถูกต้องของข้อมูลขณะทำงานจริงด้วย Zod (Runtime Validation), ไฟล์กำหนดค่า tsconfig, ชนิดข้อมูลแบบทั่วไป (Generic Types) และชนิดข้อมูลเครื่องมือช่วยเหลือ (Utility Types) โดยจำเป็นต้องแยกความแตกต่างระหว่างช่วงเวลาตรวจสอบโค้ด (Compile-time ด้วย TypeScript) และช่วงเวลาที่โปรแกรมทำงานจริง (Runtime ด้วย Zod) ให้ชัดเจนก่อนเสมอ
คำกระตุ้น (Trigger Words)
ใช้ any type ยังไง interface vs type generic Zod strict mode runtime crash type safe
ฝั่ง TypeScript (ช่วงเวลาตรวจสอบโค้ด - Compile-time)

  • ใช้เทคนิค Discriminated Union ในการจัดการและแบ่งแยกสถานะต่าง ๆ

ฝั่ง Zod (ช่วงเวลาโปรแกรมทำงานจริง - Runtime)
  • ต้องทำการตรวจสอบ (Validate) ข้อมูลที่ได้รับมาจากแหล่งข้อมูลภายนอก (External Source) อยู่เสมอ
  • ใช้คำสั่ง safeParse สำหรับการตรวจสอบข้อมูลที่ป้อนมาจากผู้ใช้งาน
  • ใช้คำสั่ง parse สำหรับการตรวจสอบตัวแปรสภาพแวดล้อมเพื่อสั่งให้ระบบหยุดทำงานทันทีหากพบข้อผิดพลาด (Crash Early)
  • นำไปประยุกต์ใช้งานร่วมกับตัวจัดการเส้นทาง (Route Handler) ทุกตัวในระบบ

API route Route Handler Server Action validate input error handling loading state waterfall pagination

  • 4. จัดการข้อผิดพลาดครอบด้วยคำสั่ง try/catch พร้อมทั้งส่งรหัสสถานะ HTTP (HTTP Status) ที่ถูกต้องเหมาะสมกลับไปในทุกกรณี

auth-guard — การยืนยันตัวตนและการรักษาความปลอดภัย (Auth & Security)

08-auth-guard
หน้าที่หลัก
ดูแลระบบยืนยันสิทธิ์ตัวตนและสถาปัตยกรรมการรักษาความปลอดภัยแบบครอบคลุมทุกระดับชั้น: ระบบรหัสโทเค็น (JWT), ระบบรักษาความปลอดภัยของคุกกี้ (Cookie Security), เครื่องมือ NextAuth, การป้องกันเส้นทางด้วย Middleware (Middleware Auth Protection) รวมถึงการควบคุมการเข้าถึงตามบทบาทหน้าที่ (RBAC) ทำหน้าที่ในลักษณะของ "ผู้ทดสอบเจาะระบบ" — วิเคราะห์และจำลองมุมมองแบบผู้โจมตีก่อนนำเสนอวิธีแก้ไขความปลอดภัย
คำกระตุ้น (Trigger Words)
auth JWT cookie NextAuth middleware protect CSRF role เช็คสิทธิ์
ระดับชั้นการรักษาความปลอดภัย (Auth Layers - จำเป็นต้องมีการตรวจสอบอย่างครบถ้วนทุกระดับชั้น)
  • ระดับชั้นที่ 1ระบบ Middleware (ไฟล์ middleware.ts) — ทำหน้าที่คัดกรองและสกัดกั้นคำขอที่ไม่ได้รับอนุญาตทันทีก่อนที่จะเข้าถึงหน้าระบบหรือระบบ API
  • ระดับชั้นที่ 2เส้นทาง API (โฟลเดอร์ app/api/*/route.ts) — ต้องมีคำสั่งเช็คสิทธิ์ auth() อยู่ที่บรรทัดแรกสุดเสมอก่อนเริ่มประมวลผลตรรกะระบบ
  • ระดับชั้นที่ 3ส่วนประกอบและหน้าเพจฝั่งเซิร์ฟเวอร์ — มีการใช้ฟังก์ชัน redirect() สั่งเปลี่ยนหน้าทันทีหากตรวจไม่พบรอบเซสชัน (Session) ก่อนที่จะเริ่มการวาดหน้าเพจ (Render)
รายการตรวจสอบความปลอดภัย (Security Checklist)
  • ✓มีการเปิดใช้งานคุณสมบัติ httpOnly cookie — รหัสโทเค็น JWT ต้องไม่ถูกจัดเก็บไว้ในพื้นที่หน่วยความจำ localStorage
  • ✓โฟลเดอร์หรือหน้าเพจที่ต้องการการปกป้อง (Protected Route) จะต้องได้รับการควบคุมผ่าน Middleware ทั้งหมด
  • ✓ไฟล์ในส่วนของ API Route ทุกตัวในระบบต้องได้รับการบรรจุคำสั่งตรวจสอบ auth() ไว้อย่างครบถ้วน
  • ✓คอมโพเนนต์ฝั่งเซิร์ฟเวอร์ (Server Component) ต้องมีตรรกะสั่งเปลี่ยนหน้าด้วยคำสั่ง redirect() ทันทีหากตรวจพบว่าไม่ผ่านสิทธิ์ก่อนเริ่มเรนเดอร์
ไฟล์อ้างอิง
ชื่อไฟล์วัตถุประสงค์การใช้งาน
references/auth-layers.mdเอกสารสำคัญที่จำเป็นต้องศึกษาและทำความเข้าใจก่อนเสมอ — รูปแบบโครงสร้างความปลอดภัยแบบเป็นระดับชั้น (Layered Auth Model)
references/cookie-security.mdข้อกำหนดคุณสมบัติการตั้งค่าคุกกี้ และแนวทางการจัดเก็บรหัสโทเค็น JWT ที่ปลอดภัย
references/rbac.mdโครงสร้างการจัดการและควบคุมสิทธิ์ตามบทบาทและหน้าที่การทำงาน (Role, Permission, Access Control)
bad-patterns/auth-mistakes.mdตัวอย่างรูปแบบที่อันตราย เช่น การเก็บ JWT ไว้ใน localStorage หรือการเขียนระบบความปลอดภัยไว้เฉพาะฝั่งผู้ใช้ (Client Side) เท่านั้น
กฎสำคัญ
  • ปฏิเสธสิทธิ์ไว้ก่อนหากเกิดกรณีที่ไม่แน่ใจหรือเงื่อนไขไม่ชัดเจน ให้กำหนดให้ระบบทำการปฏิเสธการเข้าถึงสิทธิ์ (Deny) ไว้ก่อนเสมอ
  • ต้องปกป้องทุกชั้นห้ามเขียนระบบรักษาความปลอดภัยหรือเช็คสิทธิ์ไว้เพียงระดับชั้นใดระดับชั้นหนึ่งเท่านั้น — ต้องวางระบบควบคุมไว้ให้ครบถ้วนทุกระดับชั้น
  • ห้ามใช้ LOCALSTORAGEเด็ดขาด: ห้ามแนะนำหรืออนุญาตให้มีการบันทึกหรือจัดเก็บรหัสโทเค็น JWT ไว้ในพื้นที่ localStorage ไม่ว่ากรณีใดก็ตาม

env-config — การกำหนดค่าสภาพแวดล้อม (Environment Config)

09-env-config
หน้าที่หลัก
จัดการควบคุมตัวแปรสภาพแวดล้อม (Environment Variables) ให้มีความปลอดภัยและมีโครงสร้างประเภทข้อมูลที่มั่นคง (Type-safe) การเข้าถึงตัวแปรทุกชนิดในระบบจำเป็นต้องเรียกใช้งานผ่านไฟล์ส่วนกลาง lib/env.ts ที่ได้รับการตรวจสอบความถูกต้องผ่านสถาปัตยกรรม Zod แล้วเท่านั้น — ห้ามใช้คำสั่ง process.env โดยตรงในไฟล์อื่น ดำเนินการตรวจสอบเงื่อนไขตั้งแต่ขั้นตอนการเริ่มต้นระบบ (Startup) ไม่ใช่ตรวจเมื่อตอนระบบทำงานไปแล้ว
คำกระตุ้น (Trigger Words)
env environment variable NEXT_PUBLIC .env process.env Zod env secret staging
กฎระเบียบและข้อบังคับในการใช้คำนำหน้า NEXT_PUBLIC
  • เฉพาะฝั่งเซิร์ฟเวอร์ไม่ต้องระบุคำนำหน้าชื่อตัวแปร — มีสิทธิ์เรียกใช้งานได้เฉพาะภายในส่วนประกอบฝั่งเซิร์ฟเวอร์ (Server Component), ตัวจัดการเส้นทาง API หรือโฟลเดอร์ lib/ เท่านั้น
  • ปลอดภัยสำหรับเบราว์เซอร์ต้องใส่คำนำหน้าชื่อตัวแปรด้วย NEXT_PUBLIC_ — ตัวแปรลักษณะนี้สามารถส่งออกไปยังฝั่งบราวเซอร์ได้ แต่ห้ามนำข้อมูลความลับระดับสูงมาใส่ไว้เด็ดขาด
  • กฎเหล็ก: ห้ามนำคำนำหน้า NEXT_PUBLIC_ มาใช้ร่วมกับรหัสกุญแจเข้าถึงระบบ (API Key), รหัสโทเค็นความปลอดภัย หรือรหัสผ่าน (Password) ทุกชนิด
โครงสร้างสถาปัตยกรรมไฟล์ lib/env.ts ที่ถูกต้องตามมาตรฐาน
  • 1ใส่คำสั่งนำเข้าเครื่องมือ: import z from 'zod'
  • 2เขียนโครงสร้างแผนผัง Schema เพื่อครอบคลุมและระบุชนิดข้อมูลของตัวแปรทุกตัวในระบบ
  • 3สั่งรันคำสั่ง export const env = schema.parse(process.env) — เพื่อให้ระบบหยุดทำงานทันที (Crash Early) หากตรวจพบว่าตัวแปรที่จำเป็นขาดหายไป
  • 4ไฟล์ใด ๆ ก็ตามที่ต้องการเข้าถึงค่าตัวแปรสภาพแวดล้อม จะต้องใช้คำสั่ง import { env } from '@/lib/env' เท่านั้น
กฎสำคัญ
  • เข้าผ่าน ENV.TS เท่านั้นการเรียกใช้หรือเข้าถึงตัวแปรสภาพแวดล้อมทุกชนิดต้องทำผ่านไฟล์ env.ts เท่านั้น — ห้ามเขียนคำสั่ง process.env กระจายตามไฟล์อื่นโดยตรง
  • ห้ามบันทึกไฟล์ ENV ลงคลังโค้ดห้ามทำการอัปโหลดหรือ Commit ไฟล์จริงที่ระบุค่าความลับระบบ .env ลงสู่ระบบคลังจัดเก็บโค้ด (Git) อนุญาตเฉพาะไฟล์ตัวอย่าง .env.example ที่ไม่มีข้อมูลจริงระบุไว้เท่านั้น
  • ตรวจตั้งแต่เริ่มระบบให้ Zod ทำหน้าที่วิเคราะห์และตรวจสอบเงื่อนไขทันทีที่มีการโหลดโมดูลระบบขึ้นมา — เพราะการให้ระบบหยุดทำงานตั้งแต่เนิ่น ๆ (Crash Early) ย่อมดีกว่าการปล่อยให้ระบบไปเกิดความเสียหายระหว่างทำงาน (Crash Late)
10

perf-bundle — การเพิ่มประสิทธิภาพและขนาดข้อมูล (Performance)

10-perf-bundle
หน้าที่หลัก
ดูแลและปรับแต่งระบบให้ทำงานได้อย่างมีประสิทธิภาพสูงสุด (Performance Optimization): ตรวจสอบขนาดรวมของชุดซอร์สโค้ด (Bundle Size), เทคนิคการแยกส่วนโค้ด (Code Splitting), ระบบดาวน์โหลดโมดูลแบบไดนามิก (Dynamic Imports), การเพิ่มประสิทธิภาพของไฟล์รูปภาพ, การประยุกต์ใช้คุณสมบัติ React Server Components, ระบบการโหลดฟอนต์อักษร ตลอดจนเกณฑ์ชี้วัดประสบการณ์ผู้ใช้งาน (Core Web Vitals) โดยจำเป็นต้องทำการวัดผลและระบุจุดที่เป็นคอขวด (Bottleneck) ให้ได้แน่ชัดก่อนเริ่มดำเนินการปรับแต่งเสมอ
คำกระตุ้น (Trigger Words)
bundle ใหญ่ โหลดช้า dynamic import lazy load performance LCP Core Web Vitals Lighthouse
ประเภทของปัญหาคอขวด (จำเป็นต้องวิเคราะห์และระบุให้ได้ก่อนเริ่มกระบวนการปรับปรุง)
  • ขนาดไฟล์ใหญ่เกินไปเกิดจากการใช้คำสั่ง 'use client' ครอบคลุมพื้นที่กว้างเกินไป → ส่งผลให้ต้องส่งไฟล์ JavaScript ขนาดใหญ่ไปยังเบราว์เซอร์ผู้ใช้ — แนวทางแก้ไข: ให้เลือกใช้คำสั่ง dynamic() ควบคู่กับการแยกส่วนประกอบย่อยออกเป็นใบไม้ (Leaf Component)
  • ปัญหาค่า LCP ช้าเกิดจากไฟล์รูปภาพไม่ได้รับการบีบอัดหรือจัดการอย่างมีประสิทธิภาพ → แก้ไขโดยเลือกใช้คอมโพเนนต์ next/image พร้อมระบุคุณสมบัติ priority สำหรับรูปภาพหลักของหน้า (Hero Image)
  • ปัญหาการขยับของเลย์เอาต์ (CLS)เกิดจากระบบการโหลดฟอนต์อักษรที่ไม่มีโครงสร้างรองรับสถานะระหว่างรอ (Fallback) → แก้ไขโดยเรียกใช้งานระบบ next/font พร้อมระบุรูปแบบคุณสมบัติ display: 'swap'
  • ปัญหาเรนเดอร์ซ้ำซ้อนเกิดจากการขาดหายไปของฟังก์ชันจำคำสั่งชี้เฉพาะ (useCallback) → แนวทางแก้ไข: ให้กลับไปเรียกใช้งานทักษะลำดับที่ 04 เพื่อแก้ตรรกะให้ถูกต้องก่อน แล้วจึงค่อยกลับมาปรับปรุงขนาดไฟล์ข้อมูลในภายหลัง
รายการตรวจสอบเพื่อประสิทธิภาพสูงสุด (Performance Checklist)
  • ✓การใช้คำสั่ง 'use client' จะต้องถูกจำกัดและจัดวางไว้เฉพาะในส่วนประกอบปลายทาง (Leaf Component) ที่มีความจำเป็นต้องใช้งานจริง ๆ เท่านั้น
  • ✓ส่วนประกอบที่มีขนาดใหญ่หรือประมวลผลหนัก (เช่น แผนภูมิ Chart, โปรแกรมแก้ไขเนื้อหา Editor, ระบบแผนที่ Map) ต้องเลือกใช้ฟังก์ชัน dynamic() ควบคู่กับการแสดงโครงร่างรอโหลด (Loading Skeleton)
  • ✓องค์ประกอบที่เป็นรูปภาพทุกจุดในระบบต้องเปลี่ยนมาใช้งานคอมโพเนนต์ next/image ทั้งหมด — ห้ามใช้งานแท็กอิมเมจแบบมาตรฐาน <img> ทั่วไป
  • ✓นำระบบ next/font เข้ามาใช้ทดแทนรูปแบบการเรียกใช้ฟอนต์ผ่านคำสั่ง @import หรือแท็กการเชื่อมโยงข้อมูลแบบเก่า <link>
  • ✓ปรับเปลี่ยนรูปแบบการเขียนดึงข้อมูลมาเป็นกระบวนการแบบขนาน (Parallel Fetch) แทนรูปแบบการเขียนรอคำสั่งแบบเรียงลำดับไปทีละรายการ (Sequential Await)

กฎสำคัญ
  • ต้องวัดผลก่อนเสมอจำเป็นต้องสอบถามและระบุจุดที่เป็นคอขวดที่แท้จริงให้พบก่อนเสมอ — ห้ามลงมือปรับแต่งระบบโดยอ้างอิงจากความรู้สึกหรือข้อสมมติฐานเด็ดขาด
  • ยึดค่าเซิร์ฟเวอร์เริ่มต้นกำหนดให้ระบบคอมโพเนนต์ฝั่งเซิร์ฟเวอร์ (Server Component) เป็นค่าเริ่มต้นของระบบเสมอ — จะพิจารณาใส่คำสั่ง 'use client' เฉพาะเมื่อมีความจำเป็นจริง ๆ เท่านั้น
  • ต้องแสดงผลเปรียบเทียบในการปรับปรุงประสิทธิภาพทุกครั้ง จำเป็นต้องแสดงซอร์สโค้ดในรูปแบบก่อนทำและหลังทำ (Before/After Code) ควบคู่กับรายงานการประเมินผลกระทบที่จะเกิดขึ้นกับระบบให้ชัดเจน
